# V8 到维修云端安全传输工具实施计划

> 适用代码目录：`../../repairsys/`。

## 1. 文档目的

本文档用于指导开发一套类似现有 `V8_connection` 的独立传输工具，把 V8 `rjfinshed` 中维修系统需要的基础资料安全传到维修云端。

本方案从一开始就按公网部署设计，本地试运行和正式上线使用同一套数据契约、验签规则和快照发布流程，避免上线后重做核心架构。

## 2. 已确认的业务要求

1. 维修系统运行时不能直接连接或查询 V8 的 `rjfinshed` 数据库。
2. V8 数据库继续放在工厂内网，不开放公网端口。
3. 内网工具使用只读数据库账号读取指定表，由内网主动向云端发起 HTTPS 请求。
4. 云端部署独立的 V8 接收服务，形式上类似现有 `V8_connection`，但使用更严格的签名、防重放、快照校验和回滚机制。
5. 第一版同步两个独立数据集：
   - `machine_component_bindings`：机台与零件绑定基础资料。
   - `model_photo_config`：机型、可选维修物料和机型与物料的配置关系。
6. 客户端选择维修物料时，只展示配置项名称；编号、拍照要求、OCR 配置等说明不在客户端展示。
7. 云端收到新数据后不能直接覆盖正在使用的数据。必须先暂存、校验，再原子发布；失败时继续使用上一版。

## 3. 架构结论

这个工具必须由“内网采集端”和“云端接收端”两部分组成，不能只把一个程序放到云端。

```text
工厂内网

rjfinshed MySQL
    |
    | 只读账号，只允许指定表 SELECT
    v
repair-v8-agent（Windows 服务/计划任务）
    |
    | 主动发起 HTTPS 443
    | mTLS + HMAC 签名 + 防重放 + 幂等键
    v
公网云端

sync.example.com / Nginx/WAF
    |
    | 仅代理 /api/integrations/v8/*
    v
repair-v8-connection（独立接收服务，仅监听 127.0.0.1）
    |
    | 暂存 -> 校验 -> 原子发布
    v
维修云端 MySQL / Redis
    |
    v
维修 API -> 客户端前端、管理端前端
```

云端接收端绝不反向连接工厂，不保存 V8 数据库密码，也不要求给工厂路由器开放入站端口。即使云端服务被扫描，也无法借此直接进入 V8 内网。

## 4. 与现有 V8_connection 的关系

现有 `F:\V8\V8_connection` 可以参考以下做法：

- 独立部署在云端。
- 只监听回环地址，由 Nginx 暴露指定路径。
- 使用独立、低权限的云端 MySQL 用户。
- 使用幂等键和操作日志。
- V8 本地主动调用云端，云端不连接 V8 本地库。

维修传输工具需要在此基础上增加：

- 不再只使用一个固定 API Key，改为 HMAC 请求签名。
- 增加时间戳和随机数，防止已截获请求被重复提交。
- 正式环境增加双向 TLS（mTLS）客户端证书。
- 请求体增加 SHA-256 摘要、记录数和数据契约版本。
- 数据先进入快照暂存区，校验通过后才发布。
- 增加异常数量下降保护、版本回滚和同步告警。
- 严格执行字段白名单，避免把 V8 中不需要的客户和 OCR 信息传到云端。

建议新建以下目录，保持与维修主系统解耦：

```text
integrations/
  contracts/
    v8-machine-bindings-v1.schema.json
    v8-model-photo-config-v1.schema.json
  repair-v8-agent/
    内网采集、转换、签名、重试程序
  repair-v8-connection/
    云端接收、验签、校验、发布服务
```

## 5. 同步数据范围

### 5.1 机台与零件绑定

来源表：`rjfinshed.machine_component_bindings`。

第一版允许上传的字段如下：

| 云端字段 | V8 来源字段 | 用途 |
|---|---|---|
| `sourceBindingId` | `id` | 来源追踪，不作为云端自增主键 |
| `bindingKey` | `binding_key` | 绑定关系唯一键 |
| `machineNo` | `machine_no` | 维修申请的机台识别 |
| `machineBatchNo` | `machine_batch_no` | 辅助追踪 |
| `modelName` | `model_name` | 机型匹配 |
| `machineStatus` | `machine_status` | 判断档案状态 |
| `deliveryDate` | `delivery_date` | 保修判断 |
| `outboundAt` | `outbound_at` | 出库时间追踪 |
| `materialCode` | `material_code` | 物料类型编码 |
| `materialName` | `material_name` | 维修物料名称 |
| `materialType` | `material_type` | 物料分类 |
| `materialSpec` | `material_spec` | 规格 |
| `componentSerialNo` | `component_serial_no` | 零件编号匹配 |
| `instanceBatchNo` | `instance_batch_no` | 零件批次 |
| `instanceFlowNo` | `instance_flow_no` | 零件流水号 |
| `positionCode` | `position_code` | 机台位置编码 |
| `positionName` | `position_name` | 位置名称 |
| `boundAt` | `bound_at` | 绑定日期 |
| `active` | `active` | 当前是否有效 |
| `sourceUpdatedAt` | `updated_at` | 来源更新时间 |

第一版明确不上传以下字段：

- `customer`、`agent`、`location_code`。
- `file_name`、`recognized_value`、`manual_value`、`confidence`。
- `source_task_id`、`source_file_id`、`source_ocr_result_id`。
- `check_status`、`reviewed_by`、`reviewed_at`。

原因是维修系统的绑定验证不需要客户地址、OCR 原始结果、照片文件名和审核人员信息。以后如果业务确实需要，应升级数据契约版本，不允许临时把整行数据库记录直接上传。

### 5.2 机型与维修物料配置

来源表：

- `rjfinshed.model_dictionary`
- `rjfinshed.photo_item_library`
- `rjfinshed.model_photo_config`

第一版上传以下信息：

- 机型：来源 ID、机型名称、启用状态、排序。
- 配置项：`position_code`、`item_name`、启用状态、排序。
- 绑定关系：机型来源 ID、`position_code`、是否必选、启用状态、排序。

第一版不上传拍照要求、OCR 规则、OCR Profile、备注和维护人员信息。客户端只使用配置项名称和绑定关系。若后台以后需要管理拍照或 OCR 规则，再单独新增 `schemaVersion=2`，不改变第一版接口含义。

## 6. 快照数据契约

当前数据量较小，第一版采用完整快照，不做逐条写入。完整快照能够明确表达“新增、修改、失效和删除”，也便于核对及回滚。

请求体公共结构：

```json
{
  "schemaVersion": "1.0",
  "datasetType": "machine_component_bindings",
  "snapshotId": "018f...uuidv7",
  "generatedAt": "2026-07-16T10:30:00+08:00",
  "source": {
    "system": "V8",
    "database": "rjfinshed",
    "queryVersion": "machine-bindings-v1"
  },
  "recordCount": 17,
  "recordsSha256": "64位小写十六进制摘要",
  "records": []
}
```

要求：

- `schemaVersion` 必须在云端允许列表中。
- `datasetType` 只允许已登记的数据集类型。
- `snapshotId` 全局唯一，推荐 UUIDv7。
- `generatedAt` 使用带时区的 ISO 8601 时间。
- `recordCount` 必须等于实际数组长度。
- `recordsSha256` 对规范化后的 `records` JSON 计算。
- 字段顺序、空值、日期格式和排序方式在共享 JSON Schema 中固定。
- 未声明字段默认拒绝，防止无意上传敏感列。
- 相同内容摘要不重复发布，只记录一次“无变化”同步结果。

两个数据集分别发布、分别保存当前版本。机型配置发布失败时不影响现有绑定快照，绑定发布失败时也不影响现有机型配置。

## 7. 传输认证协议

### 7.1 网络层

本地测试允许在同一台机器的回环地址使用 HTTP。任何经过局域网或公网的传输必须满足：

- 仅使用 HTTPS 443，TLS 1.2 或 TLS 1.3。
- 证书必须由受信任 CA 签发，内网代理禁止跳过证书校验。
- 正式公网环境启用 mTLS。Nginx 校验代理端客户端证书。
- V8 MySQL 的 3306、维修 API 的内部端口和接收服务端口不得暴露公网。

### 7.2 请求签名

每次请求必须包含：

```http
X-V8-Client-Id: factory-v8-01
X-V8-Key-Id: 2026-01
X-V8-Timestamp: 1784178600
X-V8-Nonce: <随机 UUID>
X-V8-Content-SHA256: <请求体 SHA-256>
X-V8-Signature: <Base64 HMAC-SHA256>
Idempotency-Key: <snapshotId>
Content-Type: application/json
Content-Encoding: gzip
```

签名原文固定为：

```text
HTTP_METHOD\n
REQUEST_PATH\n
CLIENT_ID\n
KEY_ID\n
TIMESTAMP\n
NONCE\n
IDEMPOTENCY_KEY\n
CONTENT_SHA256
```

签名使用每个采集端独立的 32 字节以上随机密钥。云端使用常量时间比较签名，并执行以下检查：

- 时间戳与服务器时间差不超过 5 分钟。
- 同一 `clientId + nonce` 在有效期内只能使用一次。
- `Idempotency-Key` 重试时请求摘要必须完全相同。
- 请求头摘要与实际请求体摘要一致。
- 客户端、密钥版本、证书状态均有效。
- 连续验签失败触发限流和告警。

HMAC 密钥不得存进源码、Git、普通 JSON 配置或日志。内网端保存到 Windows Credential Manager；云端保存到云密钥管理服务或仅管理员可读的环境密钥文件。密钥轮换时允许新旧 `keyId` 短暂并存，确认新密钥生效后吊销旧密钥。

## 8. 云端接口设计

### 8.1 采集端接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/health` | 只返回服务状态和版本，不返回数据库信息 |
| `POST` | `/api/integrations/v8/snapshots` | 上传一个完整数据集快照 |
| `GET` | `/api/integrations/v8/snapshots/{snapshotId}` | 查询本采集端上传结果 |

上传成功响应示例：

```json
{
  "snapshotId": "018f...",
  "datasetType": "machine_component_bindings",
  "status": "activated",
  "recordCount": 17,
  "contentChanged": true,
  "receivedAt": "2026-07-16T10:30:02+08:00"
}
```

状态限定为：

- `received`：已接收，等待处理。
- `validating`：正在校验。
- `rejected`：校验失败，未影响当前数据。
- `waiting_manual_approval`：触发数量下降等保护，等待管理员确认。
- `activated`：已发布。
- `no_change`：内容与当前版本相同。
- `rolled_back`：该版本已被回滚。

采集端接口不使用浏览器 Cookie，不配置 CORS，不接受客户端或管理端登录会话代替集成签名。

### 8.2 管理端接口

管理端继续使用维修系统的管理员会话和 `MASTER_DATA` 权限：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v8/sync-tasks` | 查看同步记录和失败原因 |
| `GET` | `/api/v8/snapshots` | 查看快照版本、数量和摘要 |
| `POST` | `/api/v8/snapshots/{id}/activate` | 人工确认异常快照并发布 |
| `POST` | `/api/v8/snapshots/{id}/rollback` | 回滚到指定历史版本 |
| `GET` | `/api/v8/connector-status` | 查看最近心跳、证书和同步状态 |

人工发布和回滚必须写入操作日志，记录管理员、时间、旧版本、新版本和原因。

## 9. 云端数据表规划

现有 `v8_sync_tasks` 只能记录简单结果，需要扩展或迁移为以下结构：

| 表 | 用途 |
|---|---|
| `v8_integration_clients` | 采集端编号、状态、证书指纹、当前密钥版本；不保存明文密钥 |
| `v8_sync_snapshots` | 每次上传的元数据、摘要、数量、状态和错误摘要 |
| `v8_machine_binding_snapshot_rows` | 按 `snapshot_id` 保存绑定快照行 |
| `v8_model_snapshot_rows` | 按 `snapshot_id` 保存机型 |
| `v8_photo_item_snapshot_rows` | 按 `snapshot_id` 保存维修物料选项 |
| `v8_model_photo_binding_snapshot_rows` | 按 `snapshot_id` 保存机型与选项关系 |
| `v8_active_snapshots` | 每个数据集当前启用的 `snapshot_id` |
| `v8_idempotency_keys` | 幂等键、请求摘要和原始响应 |
| `v8_request_nonces` | 防重放随机数及过期时间；多实例时优先放 Redis |
| `v8_sync_audit_logs` | 接收、拒绝、发布、回滚和密钥操作日志 |

发布动作只更新 `v8_active_snapshots` 指针，并在一个数据库事务中完成。旧快照不立即删除，因此发布失败或业务发现异常时可以快速回滚。

默认保留策略：

- 至少保留最近 30 个成功版本。
- 成功版本和审计日志至少保留 180 天。
- 被拒绝的原始载荷不长期保存，只保留校验错误、摘要和必要的脱敏定位信息。
- 数据库磁盘和备份启用静态加密，备份不放在 Web 根目录。

## 10. 快照校验和发布规则

云端接收快照后按以下顺序处理：

1. 校验 mTLS 客户端证书。
2. 校验请求大小、Content-Type 和 gzip 解压上限，防止压缩炸弹。
3. 校验客户端状态、时间戳、nonce、幂等键和 HMAC 签名。
4. 校验 JSON Schema，拒绝未知字段和超长字段。
5. 校验 `recordCount`、内容摘要和唯一键。
6. 校验业务规则和跨表引用。
7. 写入暂存快照。
8. 与当前版本比较数量、机器数、机型数及变更比例。
9. 满足自动发布条件时，在事务中切换活动快照。
10. 写入同步审计日志并返回确定结果。

第一版自动拦截规则：

- 空快照禁止自动发布。
- `bindingKey`、`machineNo + positionCode` 出现重复时拒绝。
- 绑定中的 `machineNo`、`positionCode` 或 `componentSerialNo` 为空时拒绝。
- 机型绑定引用了不存在或未启用的配置项时拒绝。
- 新记录数少于当前版本的 70% 时进入人工确认，不自动覆盖。
- 机器数量或机型数量一次下降超过 30% 时进入人工确认。
- 来源时间明显早于当前活动版本时拒绝，防止旧数据覆盖新数据。
- 未识别的数据契约版本直接返回 `422`。

维修运行时只查询活动快照。任何接收、校验或发布错误都不得清空当前活动数据。

## 11. 内网采集代理设计

### 11.1 运行方式

第一版建议使用 Python 开发，与现有 `V8_connection` 的维护技术栈接近，并可用 PyInstaller 打包为 Windows 可执行程序。

支持两种启动方式：

- Windows 服务：推荐正式环境，开机自启、无人值守。
- Windows 任务计划程序：适合第一阶段试运行和排错。

默认同步频率建议：

- 机台与零件绑定：每 10 分钟检查一次。
- 机型与维修物料配置：每 30 分钟检查一次。
- 支持管理人员手工执行一次全量同步。
- 没有数据变化时只上报 `no_change`，不生成新活动版本。

### 11.2 数据库权限

为采集代理创建独立只读账号，只授予以下表的 `SELECT`：

- `machine_component_bindings`
- `model_dictionary`
- `photo_item_library`
- `model_photo_config`

禁止使用 `root`，禁止 `INSERT`、`UPDATE`、`DELETE`、`ALTER`、`FILE` 等权限。MySQL 账号限制来源为采集代理所在机器的固定内网 IP。

建议把正式查询固化为版本化 SQL 文件，查询时使用一致性读事务。工具启动时检查必需表和字段，发现 V8 表结构变化时停止本次上传并告警，不能猜测字段继续发送。

### 11.3 本地状态和失败重试

代理在本地维护一个小型 SQLite 状态库，只记录：

- 最近成功快照 ID 和摘要。
- 待重试任务、重试次数和下次重试时间。
- 最近一次错误类型和时间。

数据库查询失败、断网、云端 `5xx` 或超时时，使用指数退避重试，例如 1 分钟、5 分钟、15 分钟、1 小时，随后按小时重试。`4xx` 数据或签名错误不无限重试，应停止该版本并告警。

待发送快照如需落盘，目录 ACL 只允许运行服务的 Windows 账号访问；上传成功后按保留策略清理。日志禁止记录数据库密码、签名密钥、完整请求体和客户敏感字段。

## 12. 云端部署方案

建议使用独立域名，例如 `sync.repair.example.com`，与公开客户端和管理端域名分开。

```text
公网 443
  -> Nginx/WAF
     -> mTLS 客户端证书校验
     -> 请求体大小限制、IP/客户端限流
     -> 127.0.0.1:8003 repair-v8-connection

repair-v8-connection
  -> 云端 MySQL：只访问 V8 快照、幂等和审计表
  -> Redis：nonce、防重放和跨进程限流

repair API 127.0.0.1:3101
  -> 只读取活动快照及正常维修业务表
```

部署要求：

- 云服务器防火墙只开放 80/443；80 仅用于跳转 HTTPS 或证书验证。
- MySQL、Redis、维修 API 和接收服务只监听回环或私有网络。
- Nginx 只把 `/api/integrations/v8/` 转发给接收服务，不暴露调试接口和 API 文档。
- 容器或 systemd 使用非 root 用户运行，文件系统尽量只读。
- 接收服务使用独立的低权限数据库账号。
- 生产环境关闭详细错误堆栈，响应不回显 SQL、表结构、主机或配置。
- 云端日志集中保存并设置异常告警；日志访问只授予运维人员。
- mTLS 证书、HMAC 密钥和数据库密码建立轮换和吊销流程。

## 13. 与当前维修系统的衔接

当前维修系统读取：

- `data/v8-machine-bindings.snapshot.json`
- `data/v8-photo-config.snapshot.json`

开发时增加统一的 `SnapshotRepository` 数据访问层：

- 本地试运行：允许从 JSON 文件读取，便于断开 V8 独立测试。
- 本地联调：接收服务可写入本地 MySQL，并可导出兼容 JSON 供人工核对。
- 正式云端：维修 API 直接读取 MySQL 中的活动快照，不依赖服务器本地文件。

这样客户端选择维修物料、机台与零件绑定查询、保修判断都通过同一个仓储接口获取数据，部署到云端时只切换配置，不修改页面业务逻辑。

现有 `POST /api/v8/sync-tasks` 允许管理员手工伪造“成功”记录，不适合作为真实同步接口。实施时应停用该写接口或改成只读展示，由接收服务根据真实结果生成同步记录。

## 14. 管理端功能

“V8 同步”管理页第一版需要具备：

- 当前活动版本、来源生成时间、接收时间和记录数。
- 内网代理最近心跳、最近成功时间、连续失败次数。
- 两个数据集各自的同步状态。
- 失败原因和被拒绝记录的脱敏定位信息。
- 新旧版本的新增、修改、失效和数量变化摘要。
- 对异常下降快照执行人工确认发布。
- 选择历史成功版本回滚，并要求填写原因。
- 下载脱敏后的校验报告，不允许下载原始 V8 整库数据。

只有拥有 `MASTER_DATA` 权限的管理员可以查看；发布和回滚建议再增加独立权限 `V8_SYNC_PUBLISH`，避免普通基础资料管理员误操作。

## 15. 实施阶段

### 阶段 0：字段确认和安全准备（0.5 至 1 人日）

## 16. 验收标准

### 16.1 业务验收

- V8 新增或修改机台绑定后，在设定同步周期内出现在维修管理端。
- 客户端选择机型后，只显示该机型绑定的维修物料名称。
- 客户提交维修时，机台和零件绑定验证使用最新活动快照。
- 无效、重复或旧版本数据不能覆盖当前正确数据。
- 管理员可以查看每次同步结果并回滚到上一成功版本。

### 16.2 安全验收

- 云端无法主动访问 V8 数据库，V8 MySQL 不存在公网监听。
- 未带有效客户端证书和签名的上传请求返回 `401` 或 `403`。
- 重放相同请求不会重复写入或重复发布。
- 修改请求体任何一个字节后，摘要或签名校验失败。
- 上传额外的 `customer`、`file_name`、`recognized_value` 等字段时，Schema 校验拒绝请求。
- 浏览器登录 Cookie 不能调用集成上传接口。
- 日志、错误响应和管理页面不显示密钥、数据库密码或完整敏感载荷。
- 3101、8003、3306、6379 等内部端口不能从公网访问。

### 16.3 可靠性验收

- 工厂断网 24 小时后恢复，代理能够自动重试并只发布一次。
- 云端接收过程中崩溃，不会产生半个活动快照。
- 发布新版本失败时，客户端继续使用上一成功版本。
- 数量骤降超过阈值时进入人工确认，不自动清空资料。
- 回滚后维修查询立即恢复到指定版本，并保留完整审计记录。

## 17. 上线顺序

1. 先在本机启动云端接收服务和测试 MySQL，使用现有两份 JSON 快照模拟上传。
2. 验证接收、校验、发布、拒绝和回滚，不连接真实 V8。
3. 在工厂内网用只读账号运行采集代理，只生成本地转换结果，不上传。
4. 将转换结果与当前快照逐字段比对，确认无敏感字段和数据缺失。
5. 连接本地接收服务完成端到端试运行。
6. 部署云端测试环境，启用 HTTPS、HMAC 和 mTLS，连续观察至少 3 天。
7. 正式环境先以“上传后人工发布”运行，确认稳定后再开启符合规则的自动发布。
8. 上线后保留旧 JSON 快照作为短期应急回退，但不再人工长期维护。

## 18. 当前不在第一版范围内

- 云端直接访问 V8 内网数据库。
- 维修系统向 V8 反向写入维修结果。
- 上传 V8 图片、OCR 原始结果或客户完整资料。
- 逐条实时消息队列同步。
- 多工厂、多 V8 数据源的冲突合并。

这些能力可以在现有 `clientId`、`datasetType`、版本化契约和快照框架上扩展，不需要改变第一版的安全边界。

## 19. 最终建议

第一版应直接完成“内网只读代理 + 云端独立接收服务 + 完整快照 + 原子发布 + 回滚”。不要先做一个把 JSON 文件直接 POST 到维修 API 并立即覆盖的临时版本，因为这种方式上线后必然还要重做认证、幂等、异常数据保护和多实例数据一致性。

正式上线的最低安全组合为：HTTPS、HMAC、防重放、幂等、字段白名单、低权限数据库账号、活动快照原子切换和审计日志；mTLS、Redis 跨实例限流及云密钥管理应在公网正式启用前完成。
