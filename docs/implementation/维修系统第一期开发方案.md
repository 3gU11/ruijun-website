# 维修系统第一期开发方案

> 适用代码目录：`../../repairsys/`。

## 1. 项目定位

本系统第一期先做“维修业务闭环 + 保修编号绑定追溯”，暂不做仓库领料、借还件、库存扣减、财务结算等复杂模块。

第一期的核心目标是：

> 代理商提交维修申请后，工厂可以审核，维修部可以处理维修工单，系统可以根据机床编号和零部件编号判断保修关系，并记录整个维修过程、维修结果、物流单号和历史追溯。

这套系统的真正核心不是单纯记录“维修单”，而是建立一套可追溯的编号绑定体系：

- 一台机床可以绑定多个板卡。
- 一台机床也可以绑定多个不同类型的零部件。
- 每个板卡或零部件都有自己的编号、批次、来源和保修状态。
- 后续维修时，系统可以判断该编号是否属于这台机床，是否还在保修期内，是否发生过更换或异常流转。

## 2. 第一期范围

### 2.1 本期要做

- 代理商维修申请
- 工厂审核
- 维修工单
- 维修处理与结果登记
- 寄回物流单号登记
- 基础报表
- 机床编号、板卡编号、零部件编号绑定
- 从 V8 系统抓取基础数据
- 预留新增物料/零部件接口
- 维修历史追溯

### 2.2 本期暂不做

- 仓库领料
- 借用配件
- 归还核销
- 15 天未还自动转销售
- WMS/立库对接
- 财务收款结算
- 快递接口自动查询
- 微信小程序
- 复杂审批流引擎

这些功能后续可以作为第二期、第三期扩展。

## 3. 第一版业务流程

```mermaid
flowchart LR
    A[代理商提交维修申请] --> B[填写机床编号和零部件编号]
    B --> C[系统查询绑定关系]
    C --> D[工厂审核]
    D --> E{是否受理}
    E -->|驳回| F[退回代理商修改或结束]
    E -->|通过| G[生成维修工单]
    G --> H[维修部检测维修]
    H --> I[登记维修结果]
    I --> J[如有更换则更新绑定记录]
    J --> K[填写寄回物流单号]
    K --> L[维修单归档]
    L --> M[报表和历史追溯]
```

## 4. 核心模块设计

## 4.1 代理商维修申请

代理商端是维修业务入口。第一版可以先做网页端，不急着做小程序。

### 应该做什么

代理商可以：

- 登录系统。
- 新建维修申请。
- 填写客户信息。
- 填写机床编号。
- 填写一个或多个送修零部件编号。
- 选择零部件类型，例如板卡、电机、驱动器、变频器、传感器、模块等。
- 填写故障描述。
- 上传图片附件。
- 填写寄出物流单号。
- 查看维修进度。
- 查看维修结果和寄回物流单号。

### 关键字段

维修申请单：

| 字段 | 说明 |
|---|---|
| 申请单号 | 系统自动生成 |
| 代理商 | 当前登录代理商 |
| 客户名称 | 最终客户 |
| 联系人 | 客户或代理商联系人 |
| 联系电话 | 联系方式 |
| 机床编号 | 保修判断核心字段 |
| 故障描述 | 代理商填写 |
| 送修方式 | 寄回、随车带回、自带 |
| 寄出快递公司 | 可选 |
| 寄出快递单号 | 可选 |
| 附件 | 图片、检测照片 |
| 状态 | 当前流程状态 |
| 创建时间 | 提交时间 |

维修申请明细：

| 字段 | 说明 |
|---|---|
| 申请单号 | 关联主单 |
| 物料编号 | 板卡或零部件编号 |
| 物料类型 | 板卡、驱动器、电机等 |
| 物料名称 | 可由系统带出，也可手工填写 |
| 规格型号 | 可选 |
| 故障现象 | 该零部件的故障描述 |
| 是否已绑定 | 系统判断 |
| 是否在保 | 系统初步判断 |

### 怎么做

- 一张维修申请单允许添加多个维修明细。
- 每条明细对应一个板卡或零部件编号。
- 代理商提交后，系统状态变为 `待工厂审核`。
- 如果编号在系统里找不到，允许提交，但标记为 `未建档`。
- 如果编号和机床编号不匹配，允许提交，但标记为 `绑定异常`。
- 工厂审核时再决定是否受理。

## 4.2 工厂审核

工厂审核是第一道内部关口，主要判断申请是否有效、是否在保、是否需要维修部处理。

### 应该做什么

工厂审核员可以：

- 查看待审核维修申请。
- 查看机床编号、零部件编号、绑定关系。
- 查看系统给出的保修判断。
- 查看 V8 抓取过来的原始资料。
- 审核通过、驳回或要求补充资料。
- 指定维修部门。
- 填写审核意见。

### 审核结果

| 审核结果 | 说明 |
|---|---|
| 通过 | 生成维修工单 |
| 驳回 | 申请结束，代理商可查看原因 |
| 补充资料 | 退回代理商补充图片、编号、描述 |
| 转人工确认 | 编号异常，需要内部确认 |

### 保修判断提示

系统审核时给出提示，不建议第一版完全自动决定：

| 判断结果 | 说明 |
|---|---|
| 在保 | 编号绑定正确，且在保修期内 |
| 出保 | 超过保修期 |
| 未建档 | 系统没有找到该编号 |
| 绑定不一致 | 零部件编号不属于该机床 |
| 信息不完整 | 缺少日期、客户或编号数据 |

### 怎么做

- 审核通过后自动生成维修工单。
- 驳回必须填写原因。
- 补充资料时，代理商可以修改后再次提交。
- 所有审核动作记录操作日志。

## 4.3 维修工单

维修工单是内部维修部执行维修的单据。

### 应该做什么

维修人员可以：

- 查看分配给维修部的工单。
- 接单。
- 登记检测结果。
- 登记维修方案。
- 登记维修结果。
- 标记是否更换零部件。
- 如发生更换，填写旧件编号和新件编号。
- 上传维修后图片。
- 标记维修完成、无法维修或检测无故障。

### 关键字段

| 字段 | 说明 |
|---|---|
| 维修工单号 | 系统自动生成 |
| 关联申请单号 | 来源申请 |
| 维修部门 | 电器维修、机械维修、研发处理等 |
| 维修人员 | 接单人员 |
| 检测结果 | 维修部填写 |
| 维修方案 | 处理方案 |
| 维修结果 | 已修复、无法维修、无故障等 |
| 是否更换零部件 | 是/否 |
| 完成时间 | 维修完成时间 |
| 备注 | 补充说明 |

### 维修结果类型

- 已修复
- 无法维修
- 检测无故障
- 建议更换
- 转研发处理
- 退回不处理

### 怎么做

- 维修工单由审核通过后自动生成。
- 维修人员不能直接创建没有申请来源的工单。
- 维修完成时，如果发生更换，必须进入“编号更换记录”。
- 维修完成后状态变为 `待寄回`。

## 4.4 物流单号登记

第一版不接快递接口，只做手工登记。

### 应该做什么

内部人员可以：

- 填写寄回方式。
- 填写寄回快递公司。
- 填写寄回快递单号。
- 填写寄回时间。
- 上传快递单照片，可选。

### 关键字段

| 字段 | 说明 |
|---|---|
| 寄回方式 | 快递、随车带回、自提 |
| 快递公司 | 顺丰、德邦等 |
| 快递单号 | 手工填写 |
| 寄回时间 | 发出时间 |
| 收件人 | 可从申请单带出 |
| 收件电话 | 可从申请单带出 |
| 收件地址 | 可从申请单带出 |

### 怎么做

- 维修完成后才允许填写寄回物流。
- 填写物流后，维修单状态变为 `已寄回`。
- 确认归档后，状态变为 `已完成`。

## 5. 保修编号绑定设计

这是第一期最重要的模块。

## 5.1 设计原则

不要把系统写死成“机床只能绑定板卡”。正确做法是：

> 机床可以绑定多个不同类型的物料实例，每个物料实例都有唯一编号。

这里的“物料实例”可以是：

- 板卡
- 变频器
- 驱动器
- 电机
- 传感器
- 模块
- 线束
- 其他可追溯零部件

## 5.2 基础概念

### 机床档案

记录机器本体。

| 字段 | 说明 |
|---|---|
| 机床编号 | 唯一编号 |
| 机型 | 机床型号 |
| 客户 | 最终客户 |
| 代理商 | 所属代理商 |
| 出厂日期 | 来源于 V8 或手工维护 |
| 保修开始日期 | 可等于出厂日期或安装日期 |
| 保修结束日期 | 根据规则计算 |
| 状态 | 正常、停用、资料不完整 |

### 物料档案

记录物料类型，不代表某一个具体实物。

| 字段 | 说明 |
|---|---|
| 物料编码 | 系统物料编码 |
| 物料名称 | 例如主控板、变频器 |
| 物料类型 | 板卡、驱动器、电机等 |
| 规格型号 | 型号 |
| 是否需要编号追溯 | 是/否 |
| 默认保修月数 | 可选 |
| 来源系统 | V8、本系统新增、导入 |

### 物料实例

记录某一个具体实物。

| 字段 | 说明 |
|---|---|
| 实例编号 | 板卡编号、零部件编号、条码 |
| 物料编码 | 关联物料档案 |
| 批次号 | 批次信息 |
| 流水号 | 如有 |
| 生产/入库日期 | 可选 |
| 当前状态 | 在机、送修、已更换、报废、备用 |
| 来源系统 | V8、本系统新增、导入 |

### 机床物料绑定关系

记录某个物料实例是否属于某台机床。

| 字段 | 说明 |
|---|---|
| 机床编号 | 关联机床 |
| 实例编号 | 关联物料实例 |
| 绑定位置 | 例如电柜、主轴、X 轴等 |
| 绑定时间 | 安装或绑定时间 |
| 解绑时间 | 换下时填写 |
| 当前有效 | 是/否 |
| 绑定来源 | V8、维修更换、人工新增 |
| 关联维修单 | 如由维修产生 |

## 5.3 保修判断逻辑

第一版建议采用“系统提示 + 人工确认”的方式。

系统判断步骤：

1. 查询机床编号是否存在。
2. 查询零部件编号是否存在。
3. 查询零部件编号是否绑定在该机床上。
4. 查询绑定关系是否当前有效。
5. 查询当前日期是否在保修期内。
6. 给出保修判断提示。

判断结果：

| 结果 | 处理建议 |
|---|---|
| 在保 | 可按保修处理 |
| 出保 | 维修可收费 |
| 未建档 | 审核员人工确认 |
| 未绑定 | 审核员人工确认 |
| 已更换/已解绑 | 原则上不直接保修 |
| 编号重复 | 数据异常，需维护 |

## 5.4 维修更换逻辑

如果维修过程中更换了零部件，系统必须记录：

- 旧零部件编号
- 新零部件编号
- 更换原因
- 更换时间
- 关联维修工单
- 操作人

同时系统要自动处理绑定关系：

1. 旧件和机床的绑定关系设置为失效。
2. 新件和机床建立新的绑定关系。
3. 旧件状态变为 `已换下` 或 `送修`。
4. 新件状态变为 `在机`。

## 6. V8 数据抓取设计

第一期要给 V8 留数据同步接口。具体用哪种方式，取决于 V8 能开放什么能力。

## 6.1 可选方式

### 方式一：读取 V8 数据库

如果 V8 允许只读数据库账号，这是最直接的方式。

适合抓取：

- 机床档案
- 客户资料
- 代理商资料
- 物料资料
- 出厂记录
- 板卡/零部件编号
- 机床和零部件绑定关系

要求：

- V8 提供只读账号。
- 明确数据库类型、表结构和字段含义。
- 本系统只读，不反写 V8。

### 方式二：V8 导出 Excel/CSV

如果 V8 不方便开放数据库，可以先通过导出文件导入。

适合第一版快速落地。

要求：

- 固定导出模板。
- 系统提供导入页面。
- 导入时做编号重复检查。
- 导入后保留原始文件和导入日志。

### 方式三：V8 API 接口

如果 V8 有 API，这是长期最理想方式。

要求：

- V8 提供接口地址。
- 提供鉴权方式。
- 提供字段说明。
- 支持按更新时间增量同步。

## 6.2 本系统需要预留的同步能力

无论 V8 采用哪种方式，本系统内部统一成“数据同步任务”：

| 同步对象 | 说明 |
|---|---|
| 客户资料 | 客户名称、联系人等 |
| 代理商资料 | 代理商名称、区域等 |
| 机床档案 | 机床编号、机型、出厂日期 |
| 物料档案 | 物料编码、名称、类型 |
| 物料实例 | 板卡编号、零部件编号、批次 |
| 绑定关系 | 机床和物料实例的绑定 |

同步记录需要保存：

- 同步来源
- 同步时间
- 成功数量
- 失败数量
- 失败原因
- 原始数据摘要

## 7. 新增物料接口

由于后续不只有板卡，还会有各种零部件，所以必须预留“新增物料”和“新增物料实例”的能力。

## 7.1 新增物料档案

用于新增一种物料类型，例如新增一种驱动器型号。

接口能力：

- 新增物料编码
- 新增物料名称
- 设置物料类型
- 设置规格型号
- 设置是否需要编号追溯
- 设置默认保修月数

## 7.2 新增物料实例

用于新增一个具体零部件，例如某块板卡、某个驱动器。

接口能力：

- 新增实例编号
- 关联物料编码
- 填写批次号
- 填写流水号
- 填写来源
- 填写当前状态

## 7.3 新增绑定关系

用于把某个零部件绑定到某台机床。

接口能力：

- 选择机床编号
- 选择实例编号
- 填写绑定位置
- 填写绑定时间
- 填写绑定来源
- 保存绑定关系

## 7.4 接口设计建议

后端可以预留这些 API：

| 方法 | 地址 | 说明 |
|---|---|---|
| POST | `/api/materials` | 新增物料档案 |
| GET | `/api/materials` | 查询物料档案 |
| POST | `/api/material-instances` | 新增物料实例 |
| GET | `/api/material-instances` | 查询物料实例 |
| POST | `/api/machines/{machineNo}/bindings` | 新增机床绑定 |
| GET | `/api/machines/{machineNo}/bindings` | 查询机床绑定 |
| POST | `/api/warranty/check` | 保修判断 |
| POST | `/api/v8/sync-tasks` | 创建 V8 同步任务 |
| GET | `/api/v8/sync-tasks` | 查询同步记录 |

## 9. 状态设计

维修申请状态：

| 状态 | 说明 |
|---|---|
| 草稿 | 代理商未提交 |
| 待审核 | 已提交，等待工厂审核 |
| 待补充资料 | 工厂要求补充 |
| 已驳回 | 工厂驳回 |
| 已通过 | 审核通过 |
| 已生成工单 | 已进入维修 |

维修工单状态：

| 状态 | 说明 |
|---|---|
| 待接单 | 维修部未接单 |
| 维修中 | 正在检测或维修 |
| 待确认 | 维修结果等待确认 |
| 待寄回 | 已维修完成，等待寄回 |
| 已寄回 | 已填写物流 |
| 已完成 | 归档完成 |
| 无法维修 | 维修失败或不处理 |

物料实例状态：

| 状态 | 说明 |
|---|---|
| 在机 | 当前绑定在机床上 |
| 送修 | 正在维修 |
| 已换下 | 已从机床拆下 |
| 备用 | 可作为备用件 |
| 报废 | 不再使用 |
| 未知 | V8 导入资料不完整 |

## 10. 基础报表

第一版报表不要复杂，先做能管理维修进度和保修追溯的。

### 维修状态报表

- 今日新增申请数
- 待审核数量
- 维修中数量
- 待寄回数量
- 已完成数量

### 代理商维修统计

- 按代理商统计申请数量
- 按代理商统计完成数量
- 按代理商统计异常编号数量

### 保修判断统计

- 在保数量
- 出保数量
- 未建档数量
- 绑定异常数量

### 零部件维修统计

- 按物料类型统计维修数量
- 按物料名称统计维修数量
- 高频故障零部件排行

## 11. 权限角色

第一版建议至少有这些角色：

| 角色 | 权限 |
|---|---|
| 系统管理员 | 用户、角色、基础资料、全部数据 |
| 代理商 | 新建申请、查看自己的申请 |
| 工厂审核员 | 审核申请、查看绑定关系、生成工单 |
| 维修人员 | 处理维修工单、登记维修结果 |
| 资料管理员 | 维护机床、物料、绑定关系、V8 同步 |
| 管理查看 | 查看报表和全部维修进度 |

## 12. 开发顺序

建议按下面顺序开发：

1. 用户登录和角色权限。
2. 机床档案。
3. 物料档案。
4. 物料实例。
5. 机床和物料实例绑定关系。
6. V8 数据导入/同步接口。
7. 保修判断接口。
8. 代理商维修申请。
9. 工厂审核。
10. 自动生成维修工单。
11. 维修结果登记。
12. 零部件更换和绑定关系更新。
13. 物流单号登记。
14. 基础报表。

## 13. 技术方向

本地开发阶段：

- 后端：Spring Boot
- 前端：Vue 3 + Element Plus
- 数据库：MySQL
- 文件存储：本机目录
- 部署准备：后期再补 Dockerfile

后期部署到 `rjzkapp.com`：

- 后端打包为 Docker 镜像
- 前端构建为静态文件
- Nginx 或 Caddy 做 HTTPS 和反向代理
- MySQL 做定时备份
- 上传文件目录独立挂载

## 14. 第一版验收标准

第一版完成后，应满足：

1. 代理商可以提交一张包含多个零部件编号的维修申请。
2. 工厂审核时能看到该机床和零部件的绑定关系。
3. 系统能提示在保、出保、未建档、绑定异常。
4. 审核通过后能自动生成维修工单。
5. 维修人员能登记检测结果和维修结果。
6. 如果更换零部件，系统能记录旧件和新件，并更新绑定关系。
7. 维修完成后能填写寄回物流单号。
8. 管理人员能查看维修进度报表和保修异常统计。
9. 系统能从 V8 或导入文件中获取机床、物料、编号、绑定关系。
10. 系统支持手工新增物料、零部件实例和绑定关系。

## 15. 一句话总结

第一期先不碰仓库和领料，重点把“机床 - 多零部件编号 - 保修关系 - 维修历史 - 更换记录”这条追溯链建起来。只要这条链稳定，后面加仓库、借还、收费、WMS 对接都会顺很多。
