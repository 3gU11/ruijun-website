# CMS 可编辑能力升级方案：向 Shopify Theme Editor 的编辑体验靠拢

> **这是一份演进记录**（按时间追加，回答"为什么这么设计"）。
> 想知道**当前系统长什么样、怎么扩展**，看 `architecture/CMS-区块系统-架构与扩展指南.md`。
> 改完代码跑 `npm --prefix cms run acceptance` 做只读验收。

**日期**：2026-10-07  
**范围**：现有 Nuxt 官网 + Directus 内容工作台  
**目标**：让运营能在预览画布里安全地新增/排列/配置预定义页面区块，并实时预览、保存草稿、走审核发布；不做电商平台替换，也不开放任意代码/CSS。

---

## 1. 执行摘要

当前 CMS 已有可视化点选编辑、文字/媒体替换、列表操作、有限布局参数、实时草稿预览及审核发布。与 Shopify 的差距主要**不是“能不能点页面改内容”**，而是页面仍以 Nuxt 手写结构为主，工作台以固定页面/区块目录为主，缺少一个统一的、由数据驱动的 **Section Registry（区块注册表）+ Block schema（区块字段定义）+ 页面布局实例（section instances）**。

建议分阶段升级：

1. **先修基础阻塞**：当前“新增段落”会生成空 `id`，而保存校验要求合法且唯一的标识；新增入口也没有类型选择。先把入口改成“从可用区块库添加”，生成稳定 ID，解决新增后无法保存的风险。
2. **建立数据驱动区块模型**：代码定义允许使用的区块、字段、媒体槽位和页面范围；页面数据只保存区块实例、排序和配置。Nuxt 按注册表渲染，不根据任意 CMS 字段动态执行代码。
3. **补齐主题编辑器主流程**：大纲树、添加/删除/复制/隐藏/拖拽排序、右侧设置面板、画布点选、断点预览、撤销重做、草稿保存。
4. **分页面迁移，不推倒重写**：六个页面逐个纳入，旧 `sections[]` 先通过适配器继续读写，确保发布站点不闪断。
5. **保持设计系统边界**：编辑范围由开发定义的可用区块和字段决定；不开放任意 HTML、JS 或 CSS。Shopify Theme Editor 本身也依赖主题作者定义的 section/block schema，不是无限制自由排版。

**不建议第一期**就追求“任意拖拽任意元素”“所有 CMS 记录都变成页面 block”或“把 Shopify 整个电商后台搬进来”。这些会显著扩大数据、安全、迁移和验收范围。

---

## 2. 对标边界：Shopify 的哪一部分

本方案对标的是 **Shopify Online Store 2.0 的 Theme Editor**，不是 Shopify 商品、库存、购物车、结账、支付、订单、营销应用或电商平台能力。

Shopify 官方 JSON template 模型把页面表示为有序的 section 列表；商家可在主题编辑器中添加、移除、重排 section，每个 section 可有自己的 settings 和 blocks。区块类型及可编辑设置由主题代码/schema 定义，不是任意代码编辑。官方文档还说明 JSON template 最多 25 个 sections、每个 section 最多 50 个 blocks；没有 preset 的 section 不能由商家从编辑器添加。

官方依据：

- [Online Store 2.0](https://shopify.dev/docs/storefronts/themes/os20)
- [The theme editor](https://shopify.dev/docs/storefronts/themes/tools/online-editor)
- [JSON templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/json-templates)
- [Building with sections and blocks](https://shopify.dev/docs/storefronts/themes/best-practices/templates-sections-blocks)

本项目不必照抄 Shopify 的商品店铺模型；要借鉴的是**编辑器的信息架构、页面构成模型、操作反馈和预览闭环**。

## 3. 当前基线与先行问题

### 已有能力（基于源码审查）

- 六个官网栏目已有工作台入口；部分产品、新闻、服务、资质等内容实际维护在独立 Directus 集合中。
- 画布可以选择绑定的文字、按钮和媒体字段；有属性面板、文本/媒体工具、撤销/重做、实时草稿预览、显式保存。
- 页面编辑器已有段落字段、媒体引用、服务/理由/工艺节点等专用列表控制。
- 已有受控样式：版式模板、对齐、宽度/间距、顺序/层级、桌面/移动偏移、字号/字重/颜色、媒体裁切焦点/遮罩、响应式可见性等；数据值受范围和枚举校验。
- 有审核与发布状态机、素材用途和版权治理；草稿预览不等于公开发布。

### 关键限制

1. **页面结构主要由 Nuxt 模板决定**：CMS 字段不是通用 section/block 渲染器；部分字段即使能编辑，也可能没有对应官网展示位置。
2. **新增区块路径不完整**：`cms/extensions/content-editor-workbench/src/module.vue:4099-4101` 的 `addPageSection()` 推入 `id: ''`；`4141-4160` 的 `validateSections()` 要求 `id` 符合小写字母/数字/短横线格式且唯一。UI 也没有让用户选择区块类型或输入/自动生成有效 ID 的流程。**这应作为 P0 先修，并用真实表单保存验收。**
3. **区块类型和字段定义散落在页面映射、模板条件和工作台表单中**：新增一种通用区块要多点手动同步，易出现“后台有字段、页面不渲染”或绑定遗漏。
4. **重复列表只支持白名单内的数据数组**：`visual-editing-fields.js:10-28` 中可排序数组为 `items/features/resources/drawings`；模板声明的虚拟媒体槽位不能按普通数组任意复制/删除，这种约束应保留。
5. **媒体覆盖需按页面/槽位逐项验收**：仅有 URL 或预览 patch 不代表公开页真实读取该绑定；须同时验证画布可编辑、草稿预览效果和发布后匿名访问结果。
6. **画布编辑是桌面优先**：`visual-editing-viewport.js` 明确将非 desktop 或 ≤720px 画布设为只读。计划应补多设备预览，不要求一期就让手机端直接编辑。

**证据位置**：

- 工作台页面编辑/版式/媒体表单：`cms/extensions/content-editor-workbench/src/module.vue:266-430`
- 页面版式字段约束：`cms/extensions/content-editor-workbench/src/section-presentation.js`
- Nuxt 对页面段落的适配与受控字段：`website/shared/page-sections.mjs`
- 可排序列表限制：`cms/extensions/content-editor-workbench/src/visual-editing-fields.js:10-28`
- 编辑视口限制：`cms/extensions/content-editor-workbench/src/visual-editing-viewport.js`
- 画布绑定/只读规则：`website/composables/useCmsDraftPreview.ts`

> 本方案依据当前工作树源码，不是实时运行时扫描；本机 CMS/Nuxt/数据库当时未监听。历史媒体覆盖数不作为当前 KPI 基线，执行前要重新跑 DOM 和发布就绪审计。工作区已有其他未提交改动，实施时先核对 git status，不要覆盖或回滚无关改动。

## 4. 产品目标与非目标

### 目标

- 运营从页面预览出发，理解“页面由哪些区块组成”，无需理解 `sections.3.items.1.title` 这样的内部路径。
- 能在安全的可用区块范围内添加、删除、隐藏、复制、重排区块及区块内 blocks。
- 能修改 schema 声明的文本、链接、图片/视频、列表、间距和呈现选项，并即时看到响应式预览。
- 保存为草稿、预览、提交审核、审核发布、回滚均有清晰且可追溯的状态反馈。
- 老页面、老草稿和现有发布流程兼容；逐页面迁移且可以回退。

### 非目标（一期）

- 任意 HTML、任意 JavaScript、自由 CSS、无限制画布定位。
- 让所有业务记录（产品、资质、文章、网点）都成为匿名自由编辑的页面块；它们继续由专用集合与工作流管理，可作为受控动态数据源。
- 复刻 Shopify 的商品、库存、结账、支付、订单、应用商店等电商能力。
- 把先进制造的 75 个绝对坐标 PSD 图层直接开放给运营自由拖动；应先拆成语义组件并完成响应式设计。

## 5. 目标体验

### 编辑器布局

1. **顶部栏**：页面/模板选择、草稿状态、保存状态、撤销/重做、桌面/平板/手机预览、预览草稿、提交审核。
2. **左侧大纲**：当前页面的区块树；拖拽排序；显示隐藏、待配置、静态限制、审核风险等状态。
3. **画布**：所见即所得预览；点击页面元素后选中所属 section 或 block；保留现有文字/媒体点选机制。
4. **右侧属性面板**：由所选 section/block 的 schema 自动生成，不为每个新类型增加一套手写表单。
5. **添加区块抽屉**：展示当前模板允许使用的区块，可按分类、搜索、预览样式，再插入当前位置或大纲末尾。

### 运营操作流程

`选择页面 → 从区块库添加 → 配置 block 内容/素材 → 桌面/平板/手机预览 → 保存草稿 → 预览 → 提交审核 → 发布`

删除会显示影响范围并二次确认；隐藏是软关闭，不销毁数据；恢复旧版本要显示会丢弃的后续改动数量。

## 6. 目标技术模型

### 6.1 Section Registry：由代码定义允许的能力

每个区块组件注册一份不可由 CMS 任意扩展的 manifest：

```js
{
  type: 'media-text',
  version: 1,
  label: '图文介绍',
  category: '内容',
  allowedTemplates: ['home', 'about', 'service'],
  settingsSchema: [/* label, field, input type, required, limits */],
  blockSchema: [/* 可重复卡片的字段定义 */],
  mediaSlots: [/* role, media type, placement key, aspect ratio */],
  presentation: [/* safe preset allowlist */],
  capabilities: { addBlock: true, reorderBlock: true, duplicate: true, hide: true }
}
```

- manifest 与 Nuxt renderer 一一对应；页面只保存 `type` 和配置，不可提供组件路径、代码片段或可执行表达式。
- `allowedTemplates` 与 `disabled_on/enabled_on` 类似，控制某类区块是否能加入特定页面。
- schema 渲染控件、服务端校验、预览 patch 白名单共同消费同一份定义，避免“三套字段表”。
- 组件升级通过 `version + migration` 完成；不能默默重解释已保存的数据。

### 6.2 页面布局数据：渐进兼容现有 `pages.sections`

建议用现有 `pages.sections` JSON 逐步规范化，不在第一步新增复杂关系表：

```json
{
  "id": "sec_01J...",
  "type": "media-text",
  "version": 1,
  "enabled": true,
  "settings": { "title": "...", "body": "...", "layout": "split-media-left" },
  "blocks": [
    { "id": "blk_01J...", "type": "feature", "settings": { "title": "..." } }
  ],
  "media": [ { "role": "background", "media_asset_id": "..." } ]
}
```

兼容原则：

- 迁移适配器将旧 `id/title/body/items/media/layout` 读成新实例；旧 renderer 在迁移期仍是 fallback。
- 新区块用 `type + settings + blocks`；业务特化结构保留受控字段，不直接把所有表单改成松散 JSON。
- `id` 使用稳定唯一 ID；排序以数组顺序或明确 `order` 为准，避免重复/空 slug。
- 媒体仍使用受控 `media_asset_id`、role、用途、版权与文件授权；前台只取已批准的数据。
- 绑定业务记录使用动态数据源引用（如 `source: { collection, item_id, field }`），只能指向白名单字段，不允许任意 Directus API 查询。

### 6.3 内容与布局分层

- **页面结构**：哪些区块、顺序、是否显示。
- **区块设置**：标题、段落、按钮、颜色/版式预设。
- **区块 blocks**：卡片、FAQ、时间轴事件等重复子项。
- **业务数据源**：产品型号、文章、证书等专用实体，区块只选择/引用它们；不复制成孤立文本。
- **站点级设置**：导航、页脚、品牌/字体/色板，仍走 site settings 的单一治理入口。
- **审批发布**：页面布局和引用素材作为同一个修订预览，发布前进行一体化校验。

## 7. 分阶段实施路线

### 阶段 0：基线与 P0 修复

**目标**：先把“现有编辑结果能可靠保存、预览和验收”变成可度量基础。

- 修复“新增段落”：由区块选择器创建有合法 `id/type` 的实例；无法识别的类型禁止保存，而非悄悄生成空 ID。
- 给已有页面记录建立稳定 ID；删除、复制、移动要更新选中项和预览定位。
- 增加契约测试：可新增→保存→回读→预览；ID 唯一；不允许添加页面不支持的 section type。
- 重跑六页面文本/媒体 DOM 审计、静态槽位对账、发布就绪度报告，形成新基线；媒体统计不能把 PSD wrapper/静态装饰和真实槽位混在一起。
- 将发布预检按页面输出可行动错误：缺绑定、素材不可发布、字段未接入、宣传主张待审分别列示。

**验收**：新增一段实际可完成“插入—保存—重新加载—显示正确”，旧页面数据零丢失；覆盖率报告中所有未分类槽位都有归属。

### 阶段 1：注册表与 section/block schema

**目标**：让“可添加的内容类型”有统一契约。

- 建 Section Registry 与 `type/version/schema/renderer` 契约；先实现 `rich-text`、`media-text`、`feature-grid`、`stats`、`gallery`、`timeline`、`cta`、`faq` 等通用、安全区块。
- 每个区块定义适用页面、字段、媒体角色、尺寸/比例、可重复 blocks、响应式预设、验证规则及默认值。
- 加 schema-driven 属性面板；字段类型包括短文本、富文本（受限）、链接、图片/视频、列表、枚举、数字、开关及动态源引用。
- 对不支持的旧 `type` 采用只读 legacy renderer，并提示“需要迁移”，不可丢弃数据。

**验收**：新增一个 schema 区块时无需在 CMS Vue 文件和每个页面里复制字段表；坏类型、坏 URL、超长文本、越界样式值在保存前与服务端均被拒绝。

### 阶段 2：Shopify 风格编辑器主交互

**目标**：让用户围绕页面结构工作，而不是面对 JSON 表单。

- 新增页面大纲：section/block 树、拖放排序、插入位置、启用/隐藏、复制、删除确认。
- 新增“添加区块”抽屉：按分类、适用页面、搜索和预览选择；插入前提供简短描述。
- 右侧 Inspector 根据 schema 自动生成设置；画布点击与大纲选择双向同步。
- 多设备预览切换 desktop/tablet/mobile；任何断点都能预览；编辑可先保持 desktop-only，再逐步开放 tablet，不要求手机上编辑。
- 提供“未保存/保存中/已保存/保存失败”明确状态；自动保存仅作为恢复草稿（local/服务器 draft）不能绕过显式审核发布。
- 撤销重做支持结构变更（增删/排序/配置），不只支持字段值。

**验收**：常见编辑无需输入 section ID；添加/移动/隐藏/复制后预览和保存结果一致；刷新恢复同一草稿；撤销/重做跨文本、媒体、排序均有效。

### 阶段 3：六页面逐步迁移

建议迁移顺序：

1. **服务页**：结构内容多、重复卡片和办事处数据清晰，适合作为 schema 验证场景。
2. **关于页**：图文、历史、客户/厂区图库，验证 block 和媒体绑定。
3. **首页**：Hero、理由、产品横移、时间轴；对已绑定的 hero/reasons/history 保持公开链路测试。
4. **新闻页**：动态文章、视频媒体和文章详情动态源。
5. **产品页**：产品型号/参数继续使用专用业务集合，区块负责选取和呈现，不复制商品数据。
6. **先进制造页**：最后迁移；先把绝对坐标 PSD 拆为语义层组件（车间卡、设备图库、流程节点、装饰层），装饰层不放入可自由排序的运营 block。

每页按“新旧 renderer 双读 → 预览比对 → 指定页面灰度切换 → 发布前后抽查 → 旧 renderer 下线”执行。不可一次性把六页 `sections[]` 全重写。

**验收**：每页面可编辑项以真实 DOM 契约核实；用户编辑素材后，不仅 iframe patch 改变，公开无 cookie 页面也使用已发布值；屏幕阅读和移动响应不退化。

### 阶段 4：动态来源与可复用模块

- 支持区块字段绑定到经授权的业务记录字段（产品型号、文章、服务资料等），改变选择时预览同步刷新。
- 对导航、页脚等全局模块提供“站点级区块”，禁止各页面复制多份。
- 允许“保存为可复用 section 预设”或“全站同步”需显式确认；默认复制为独立实例，避免一个页面修改意外影响其他页。
- 支持模板变体（例如营销着陆页），但只能由开发预先注册新页面模板和可用区块集合。

**验收**：动态源字段越权不可读取；全站模块的修改范围可预览、可审计、可回滚；页面级实例与全站共享设置不会混淆。

## 8. 安全、治理与迁移要求

1. **schema 驱动，不执行用户代码**：不保存任意组件名、HTML、JS、CSS；只允许注册表中的 `type` 和字段。
2. **双端校验**：浏览器负责及时反馈，服务端重验字段、URL、媒体用途、状态、素材版权和发布门禁；不可相信前端 schema。
3. **发布快照**：草稿预览基于同一修订快照；发布需要页面与引用素材都满足门禁；记录布局版本和操作者。
4. **破坏性操作可恢复**：删除 section 默认软删除/草稿内删除；历史版本对比后明确确认；每个 publish 生成不可变版本快照。
5. **兼容策略**：保留旧字段读路径；迁移脚本 dry-run、备份、批次写、幂等；每页可回滚到旧 renderer。
6. **数据源边界**：产品价格/参数/证书/文章等权威业务数据继续在其集合管理；页面组件引用它们，不造成副本漂移。
7. **权限角色**：内容编辑可修改草稿/提交审核，管理员可发起审核但不能越过发布门禁；设计系统和注册表只由开发发布。

## 10. 主要风险与处理

- **风险：通用区块自由度损坏品牌设计** → 只开放预设 renderer/schema，区块类型、可用页面、范围由开发控制。
- **风险：结构迁移影响现有页面** → 每页渐进迁移，旧 renderer fallback、灰度、可逆 migration。
- **风险：CMS 字段可保存但公开模板不读取** → 所有字段必须有 schema renderer 与三段验证：画布可选、预览有效、公开页有效。
- **风险：动态业务记录复制过时** → 使用受控动态源引用，不复制权威字段。
- **风险：制造页设计破版** → PSD 静态艺术层保持锁定；先拆语义层、定义断点和比例约束后再开放设备照片区块。
- **风险：编辑工作流绕过审核** → 自动保存仅保存草稿；发布仍走现有审核状态机、媒体检查与审计日志。

- **P0**：修新增区块空 ID 问题 + 加入基线审计和保存回读测试。

## 12. 当前结论

建议目标不是“把 CMS 改成 Shopify”，而是：**把 Shopify Theme Editor 的成熟编辑模型引入现有 CMS，同时保留当前项目的行业内容模型、媒体治理、审核发布和设计约束。**

完成 P0–P3 后，日常编辑体验可以在“添加区块、安排页面结构、可视化配置、实时多断点预览”这些维度接近 Shopify；后台业务范围仍是企业官网 CMS，不包含 Shopify 的完整电商平台能力。

## 14. 真实服务运行验证（2026-10-07 补充）

### 结论：闭环全部跑通，并修复了 2 个只在运行时暴露的缺陷

启动完整本地栈（MySQL 3307 / MinIO 9000 / Directus 8055 / Nuxt 4175）做了真机验收。**注意：此前单测 485 + 548 全绿，但仍有两个缺陷只有真实启动才能发现。**

#### 缺陷 A — server 层跨目录相对导入在打包后失效

`website/server/services/cms-page-reader.mjs` 使用 `'../../shared/page-section-registry.mjs'`。Nitro 打包后该路径按构建产物位置解析，运行时抛 `Cannot find module 'D:\shared\page-section-registry.mjs'`，**导致所有 `/api/public/v1/pages/*` 返回 500**。

- 为什么单测没抓到：Node 原生解析相对路径正常，只有 Nitro 打包才会改变基准目录。
- 修复：`website/package.json` 增加 `"imports": { "#shared/*": "./shared/*" }`，源码改用 `#shared/page-section-registry.mjs`。同一份 specifier 在 Node 测试与 Nitro 中都能解析。
- 反面做法：不能用 `~/shared/...`（Nuxt 别名，Node 测试会挂）；也不要用非标准 `NUXT_BUILD_DIR` 规避构建目录清理（会让相对导入解析到构建目录外）。

#### 缺陷 B — Directus 扩展 dist 陈旧，预览通道跑旧逻辑

`cms/content-preview/content-preview-content.mjs` 加了 `previewSection` 的注册表分支，但引用它的 `content-preview-token-endpoint` 扩展 `dist/index.js` 仍是旧产物。结果：预览会话中自定义区块的 `type` 被抹为 `null`，Nuxt 端 fail-closed 把整块过滤掉，画布看不到新区块，且**没有任何报错**。

- 修复：重建该扩展并重启 Directus。
- 固化规则：**凡改动 `cms/content-preview/*`，必须重建引用它的扩展**。

## 15. P1 补区块类型 + P2 补编排（2026-10-07 晚）

### 注册表 schema 扩展为四种字段类型

`page-section-registry.mjs` 的 field 从「只有 text/textarea」扩展为：

| 类型 | 说明 | 附加约束 |
| --- | --- | --- |
| `text` / `textarea` | 有界字符串 | `maxLength` |
| `media` | 受控媒体引用 | `maxItems`、可选 `roles` 白名单 |
| `list` | 重复项 | `maxItems`、`itemFields`（子字段） |

**分层原则（重要）**：注册表只校验**形状**（结构、数量、角色格式）；**素材是否被授权**由服务端媒体解析器决定。不要把授权判断塞进注册表，否则会与媒体治理链路产生第二套真相。

### 新增两种区块类型

- **`image`** — 单图 + 标题 + 说明；`media` 限 1 项，角色限 `image` / `photo`
- **`card-grid`** — 标题 + 卡片列表；`media` 开放角色（每张卡用 `media_role` 声明自己的槽位），`items` 限 12 项，每项含标题/说明/配图位置

选择这两种是为了验证注册表能承载不同形态：前者是「标量 + 媒体」，后者是「列表 + 嵌套子字段 + 媒体角色绑定」。

### 四层白名单改为按字段类型分派

`publicSection`（公开读取）与 `previewSection`（草稿预览）不再硬编码 `section.media`，改为遍历注册表声明、按 `field.type` 分派输出。`resolvePageSection` 的注册表分支同样按声明复制字段。

**效果**：新增一个区块类型时，只需要在注册表里加一条定义，四层自动跟随——**不需要在页面 fallback 里加条目**。

### 工作台补齐编排能力

- media / list 字段由 schema 生成控件，复用既有受控媒体选择器与重复项编辑器（新增/上移/下移/删除）
- **拖拽排序**：仅对 registry 区块开放（legacy 区块 id 手工维护，不参与重排）
- **复制区块**：生成新唯一 ID + 拷贝已声明字段，插入到原区块之后

**顺带修复一个真实缺陷**：`visiblePageSections` 在选中分组时是过滤后的子集，而 `removePageSection(index)` 用的是 v-for 索引——**会删掉错误的区块**。已改为按对象定位真实位置（`pageSectionIndex`）。

## 17. P3 六页面迁移（2026-10-08）

### 关键决策：抽共享组件，而不是复制模板

原计划是照 `service.vue` 的模式，往其余 5 个页面各复制一份区块模板 + 样式。实际改为抽出 **`website/components/CmsCustomSections.vue`**：

| | 复制模板方案 | 共享组件方案（采用） |
| --- | --- | --- |
| 新增区块类型 | 改 6 个页面 | 改 1 个组件 |
| 样式维护 | 6 份副本，易漂移 | 1 份 |

## 18. P4 动态数据源：数据列表区块（2026-10-08）

### 这是第一个「内容不在区块里」的区块

前面三种区块（图文、图片、卡片）的内容都存在区块自身的字段里。`data-list` 不同：它只存**指向**（数据来源 + 条数 + 列数），渲染时读取该源当前的内容。页面因此能随数据自动更新，不需要有人回来重新编辑。

### 新增字段类型

| 类型 | 语义 | 拒绝条件 |
| --- | --- | --- |
| `select` | 值必须来自定义声明的 `options` 闭集 | 不在选项内、非字符串 |
| `number` | 有界整数 | 非数字、非整数、越界 |

`select` 的闭集语义是这里的关键防线——它保证区块**不可能**指向一个未注册的数据源。

### 数据源目录（`website/shared/page-section-sources.mjs`）

已注册三个源：产品系列、新闻文章、资质证书。每个源声明 endpoint、链接前缀、slug 字段。

**映射策略**：不同 reader 的字段名不一致（系列是 `name`/`positioning`，文章是 `title`/`summary`），因此映射**探测候选字段名列表**而非硬编码。新增数据源只需在目录里加一条，不用改映射逻辑。

**一个被自己测试抓到的语义错误**：`limit` 必须**在过滤之后**生效。先按 limit 截断再过滤，会导致"显示 3 条"因为前几条无效而只渲染 1 条。

### 取数策略

共享组件用 `useAsyncData` + 一个**排序后的字符串签名**作为 watch 源：

- 只请求页面真正引用到的源 —— 没有 data-list 的页面零额外请求
- 字符串签名避免 computed 重算引发的重复请求
- 单个源请求失败降级为空数组，不会拖垮整页

### 四层一致性

`publicSection`、`previewSection`、`resolvePageSection` 都补齐了 select/number 分派，并在读取层**再次校验闭集**——越界来源即使绕过工作台也到不了页面。

### 验收结果

| --- | --- |
| 单元/契约测试 | website 501/501、cms 554/554 |
| 区块库 | 新增「动态内容」分类，含「数据列表」 |
| 控件 | 来源下拉显示中文标签（产品系列/新闻文章/资质证书）；条数 1–12；列数 1–4 |
| 保存 | 成功 |

所以动态列表的「有数据」路径**无法在本地端到端验证**。已采取的替代措施：

1. 用单元测试覆盖字段映射（含不同 reader 的字段名差异、无标题记录丢弃、limit 语义）

## 19. P4 模板变体（2026-10-08）

### 机制：变体字段自动注入，而不是手写

区块定义声明 `variants` 后，注册表**自动注入** `variant` 字段：

```js
'card-grid': withVariantField({
  ...,
  variants: [
    { key: 'grid', label: '网格' },
    { key: 'list', label: '列表' }
  ]
})
// 注册表自动补上：
// { key: 'variant', label: '版式', type: 'select', options: ['grid','list'], optionLabels: {...} }
```

**为什么必须自动注入**：如果手写一个 `select` 字段，`variants` 列表和 `options` 就成了两份数据。渲染器认识的版式与运营可选的版式迟早对不上——而这种漂移不会有任何报错，只会表现为"选了某个版式但页面没变化"。自动注入让**真相只有一个**。

### 顺带的一处解耦

`select` 字段新增 `optionLabels`（key → 显示名）。工作台据此渲染中文选项，因此**不再需要 import 数据源模块**去查标签。数据源的中文名通过 `dataListSourceLabels` 走同一条路。

这消除了工作台对业务模块的直接依赖——工作台现在只认识注册表。

### 已声明变体

| 区块 | 变体 |
| --- | --- |
| 卡片列表 | 网格 / 列表 |
| 数据列表 | 网格 / 列表 / 紧凑 |

渲染层按 `cms-variant-{key}` 类应用样式，字段缺失时回退 `grid`，所以老数据不会因为缺字段而破版。

### 验收结果

| 项目 | 结果 |
| --- | --- |
| 单元/契约测试 | website 503/503、cms 554/554 |
| 工作台控件 | 「版式」下拉，选项显示中文（网格/列表），值为 grid/list，默认 grid |
| 保存 | 成功 |
| 落库核对 | `variant = list` ✓ |
| 预览渲染 | 带 `cms-variant-list` 类，未回退到默认网格（5/5） |

### 更新后的完成度

- **P1 约 85%** — 5 种字段类型、4 种区块类型
- **P2 约 90%**
- **P3 约 85%** — 6 个页面

## 20. P4 可复用预设（2026-10-08）

### 机制：声明在注册表，套用是纯数据拷贝

区块定义新增 `presets` 数组，每个预设带 `key` / `label` / `description` / `values`：

```js
presets: [
  { key: 'standard-3', label: '标准三卡', description: '三列网格，预置三张卡片',
    values: { variant: 'grid', columns: 3, items: [...] } }
]
```

注册表导出 `listPageSectionPresets()` 与 `applyPageSectionPreset()`。后者**保留 id / type / version，只覆盖预设声明的值**；未知 key 原样返回——**不做半套用**，因为半套用产生的块比不套用更难排查。

**为什么是内置预设而不是用户自建**：自建预设需要持久化 + 管理界面（还得决定存哪、谁能改、如何治理），而内置预设是纯声明式的，立刻可用、可测试、零存储成本。等真的有自建需求时再补存储层。

### 已声明预设

| 区块 | 预设 |
| --- | --- |
| 卡片列表 | 标准三卡 / 双列对照 / 纵向列表 |
| 数据列表 | 最新动态 / 产品展示 / 资质证书条 |

### 一条关键测试：每个预设都必须仍然合法

```
every declared preset produces a section that still validates
```

遍历「所有页面 × 所有区块类型 × 所有预设」，断言套用后 `validatePageSectionInstance` 返回空。

**这是预设机制的安全网。** 一个不合法的预设，会把「套用后无法保存」的坏块交给运营——而且这种问题在人工点击时极难发现，因为界面看起来一切正常。有了这条测试，新增预设时只要写错值，CI 立刻拦下。

### 构建抓到一个测试抓不到的错

写这轮代码时用了 `ref<Record<string, string>>({})`，但 `module.vue` 是**纯 JS 的 `<script setup>`**（没有 `lang="ts"`），编译直接失败：

```

```

**源码 grep 型测试完全抓不到这类错误**——它们只匹配文本，不做解析。已把「改完必须 `npm run build`」写进 skill 铁律六：构建是唯一的编译检查，构建通过 + 测试通过才算改完。

## 22. 跨页区块复用（2026-10-08）

### 先说结论：全站共享模块不该做

调研发现，**全站级的共享内容已经是组件实现的**：

| 共享内容 | 现有实现 |
| --- | --- |
| 页头 / 导航 | `SiteHeader.vue` |
| 页脚 | `PsdFooter.vue` |
| FAQ 助手 | `GlobalFaqAssistant.vue` |

8 个页面都在用这些组件。所以再做一个「全站共享模块」的 CMS 能力，**会和现有机制重复**，同时引入一个新集合和一套引用完整性规则（引用方还在用时，被引用的块被改/删怎么办）。

**判定：成本高、收益不确定，属于过度设计。**

### 真正缺的是什么

编辑者在一个页面调好一个块，想把它放到另一个页面。

这个需求用**内存剪贴板**就能满足，完全不需要引用图——因为没有引用关系，就没有引用完整性问题。

### 实现

| 组件 | 作用 |
| --- | --- |
| `copiedPageSection` | 内存剪贴板，跨栏目切换保留（工作台不重新挂载） |
| 「复制到其他页」 | 区块卡片上的按钮 |
| 「粘贴区块」 | 顶部按钮，**仅在目标页注册了该类型时出现** |
| 粘贴逻辑 | `createPageSectionInstance` 生成新 ID → 拷贝声明字段 |

粘贴出来的块是**全新实例**，与源块完全独立——改一个不影响另一个。

### E2E 踩的两个坑（已写入 skill）

**坑 1：切换栏目会被 `window.confirm` 拦住。**
有未保存改动时 `confirmDiscardChanges` 会弹确认框，而 **Playwright 默认自动取消对话框**——栏目静默地不切换，脚本却继续往下跑。表现为"点了按钮但后续找不到元素"，极难定位。

修法：`page.on('dialog', (dialog) => dialog.accept())`，并且**断言切换真的生效**（按钮带 `active` 类），否则这类失败会伪装成别的问题。

**坑 2：栏目入口名 ≠ 区块标题。**
入口按钮用的是分组标签（「关于瑞钧首屏」「发展历程里程碑」），不是 section 的 `title` 字段。用 title 去匹配必然超时。

> 第一次跑 E2E 时两个块都落在了 service 页——看起来像功能坏了，实际是脚本没处理确认框。
