> 审计时间：2026-11-11
> 对象：`cms/extensions/*`、`cms/content-workflow/*`、`website/utils/*`
> 方法：代码审阅 + 生产库权限矩阵实查 + 真实账号攻击复现
> 环境：172.21.8.71 上的 CMS（Directus 11.17.4）

## 0. 结论摘要

状态机本身设计严谨（非法跃迁抛错、`create` 强制草稿、`publication_state` 不可单独设置、状态流转禁止夹带内容修改、`postMessage` 双向校验 origin、官网富文本有白名单净化）。**发现 1 个已实测可复现的高危缺陷，已修复并验证。**

| 等级 | 数量 | 状态 |
| --- | ---: | --- |
| P0 | 1 | **已修复并复测通过** |
| P1 | 4 | 2 已修复，2 待排期 |
| P2 | 4 | 记录待办 |

> 初版报告曾把「画布 innerHTML 渲染正文」列为 P0 存储型 XSS。**复核后该结论不成立**：画布模板使用 `{{ editorialDraft.body }}`（Vue 插值自动转义），`innerHTML` 仅用于离屏 div 解析；官网侧 `v-html` 走 `renderSafeRichText` 白名单净化。此处更正。

## 1. P0-1 内容编辑绕过审核直接发布（已修复）

**根因**：`homepage_sections` 与 `repair_page_configs` 有完整的 `status` / `publication_state` 字段，也被官网 BFF 公开读取，但不在 `publicationWorkflowCollections` 保护列表内。扩展不介入后只剩权限层，而 Directus 的 `update` 过滤只校验**现有记录**状态、不校验**新值**，`create` 无状态限制。

**修复前的实测结果**（使用真实「内容编辑」角色账号）：

| 攻击 | 结果 |
| --- | --- |
| `POST repair_page_configs` + `status:"published"` | 200 SUCCESS，直接发布 |
| `POST homepage_sections` + `status:"published"` | 200 SUCCESS，直接发布 |
| `PATCH` 草稿 → `status:"published"` | 200 SUCCESS，草稿直接上线 |
| 对照组 `POST pages` + `status:"published"` | 400 BLOCKED |

**修复**：把两个集合加入 `editorCollections` 与 `publicationWorkflowCollections`（`cms/content-workflow/content-publication-workflow.mjs`）。

**修复后的复测**：

| 复测项 | 结果 |
| --- | --- |
| `POST homepage_sections` + `status:"published"` | 强制变为 `draft / unpublished` |
| `POST repair_page_configs` + `status:"published"` | 强制变为 `draft / unpublished` |
| `PATCH` 草稿 → `published` | **400 拒绝**（内容编辑只能编辑草稿或提交审核） |
| 正常流程 `draft → review` | 仍然成功，业务未受损 |

## 2. P1 缺陷

### P1-1 版本回滚可让线上内容瞬间下线（已修复）
`content-version-restore` 的回滚固定写成 `draft`。若当前是 `published`，官网会立即不再展示，而接口只要求「丢弃较新版本」的确认，没有针对已发布状态的确认。

**修复**：当前记录为 `published` 时，必须携带 `confirmUnpublishPublished: true`，否则返回 409 `PUBLISHED_CONTENT_RESTORE`。

### P1-2 重复的 Administrator 角色与策略（已修复）
库中存在 **4 个同名 `Administrator` 角色**和 **4 个 `admin_access=1` 的策略**（schema 重复应用不幂等）。

**修复**：确认只有 `27770990…` 角色绑定了 admin 用户后，保留该角色与其策略 `88e6fa65…`，删除其余 3 组（先备份，`directus_permissions` 对这些策略引用为 0）。修复后 Administrator 角色/策略各剩 1 个，admin 登录与读取正常。

### P1-3 审核人可自我批准（待排期）
`reviewerCanHandle` 只校验角色是否覆盖集合，不校验 `actor.id` 是否等于提交人。`system_admin` 可单人完成 `draft → review → scheduled → published`。缺少双人复核约束。

**建议**：在提交时记录 `submitted_by`，审核动作要求 `actor ≠ submitted_by`（可配置豁免）。

### P1-4 并发编辑丢失更新（待排期）
`filter(items.update)` 先读 `current` 再算 `next` 并写回，无乐观锁。两个并发请求基于同一 `current`，后者覆盖前者；版本表会留两条记录，但中间内容实际丢失，审计呈现与实际不符。

**建议**：客户端回传读取时的 `date_updated`，服务端比对后再写入，否则返回 409 让用户刷新。

## 3. P2 缺陷（记录待办）

1. **`reviewerCanHandle` 媒体分支是死代码**（`content-publication-workflow.mjs:63-75`）：`review_manager` 先命中集合判断返回，后面的 `reviewerRoleForMediaUsageScope` 分支永不执行，按 `usage_scope` 分级审核实际失效。
2. **版本快照含审核内部字段**：`contentSnapshot` 保留 `review_note`、`reviewed_by`；`read_only_manager` 可读全部版本，能看到审核备注。
3. **回滚不产生新版本记录**：只把原版本标为 `restored` 并改记录，审计链在「回滚」动作上不完整。
4. **`content_versions` 无清理策略**：已有 1046 条且含全量快照，会持续增长。

另：`content_submissions`（送审批次）也不在工作流保护列表，编辑可改其 `status`，会污染审核队列展示，但不会让内容真实上线，列为 P1 待办。

## 4. 已确认安全的部分

- **状态机不可跳跃**：`content_editor` 只能 `draft→draft`、`draft→review`、`rejected/unpublished→draft`，其余抛 `INVALID_TRANSITION`。
- **`create` 强制草稿**（受保护集合），即使请求带 `status:'published'` 也会被覆盖。
- **`publication_state` 不可单独设置**，返回 `PUBLICATION_STATE_DERIVED`。
- **状态流转禁止夹带内容修改**（`assertTransitionDoesNotMutateContent`）。
- **发布前最终校验**：`review→scheduled`、`scheduled→published` 均执行 `assertFinalPublicationReadiness`。
- **`postMessage` 双向校验**：CMS 端校验 `event.origin` 与 `event.source === iframe.contentWindow`；官网端校验 origin 白名单且 `event.source === window.parent`。
- **预览令牌一次性**：消费用 `where({id, status:'active'})` 条件更新，重放返回 409。
- **富文本渲染安全**：官网 `v-html` 前经 `renderSafeRichText` 白名单净化（固定标签集、img 仅站内受管路径、a 限协议）；CMS 画布用插值转义，`innerHTML` 仅离屏解析。
- **匿名角色零权限**；**所有角色均无 `delete`**，内容只能下线/归档。

## 6. 建议的后续顺序

1. 审核动作加「提交人 ≠ 审核人」约束（P1-3）
2. 内容 `update` 增加 `date_updated` 乐观锁（P1-4）
3. 把 `content_submissions` 纳入工作流或收回编辑写权限
4. 版本表加保留策略（每内容保留最近 N 条）
5. 修复 `reviewerCanHandle` 媒体分支死代码
