# Repair 客户端重构方案

## 1. 目标与边界

### 目标

将 Repair 客户端重构为面向机床客户的服务门户：客户从官网进入后能立即识别品牌归属，完成维修申请、设备/板卡核验、进度查询与保修核验，并在整个流程中获得明确的下一步。

视觉方向采用：**UpKeep 的浅色服务工作台**与**Limble 的深色当前任务舱**融合。官网的导航、排版尺度、黑白红色彩关系作为品牌基线；Repair 保持独立部署与独立业务边界。

### 不在范围内

- 不将 Repair 嵌入 Nuxt，不共享 Cookie、JWT、数据库连接或业务代码。
- 不修改 Repair API、鉴权规则、V8 机型字典和 QR 业务规则。
- 不将 CMS 变成维修流程规则的维护端。
- 不使用大面积红色统计面板、巨型 Logo 水印、持续背景线框或无业务含义的循环动效。

## 2. 信息架构

| 路由 | 页面职责 | 主任务 | 页面语境 |
|---|---|---|---|
| `/support` | 服务入口和已登录服务概览 | 发起维修、查看当前任务 | 未登录为品牌服务入口；登录后为轻量工作台 |
| `/repair/new` | 维修申请 | 建立维修档案并提交 | 深色任务标题区 + 浅色五步工作区 |
| `/requests` | 维修进度 | 理解工单当前状态并完成下一步 | 案件时间线和待办动作 |
| `/warranty` | 保修核验 | 确认设备保修状态 | 设备身份结果页 |
| `/scan/:token` | 板卡扫码 | 建立板卡、设备、保修关系 | 逐项确认的设备身份页 |

## 3. 页面结构

### 3.1 未登录服务首页

1. 官网式公共导航：服务首页、发起维修、维修进度、技术支持、返回官网、登录。
2. 服务首屏：一句明确服务承诺、唯一主按钮“发起维修申请”、次按钮“了解服务流程”。
3. 设备入口：搜索和 V8 `model_dictionary` 分组机型选择。
4. 服务入口带：维修进度、保修核验、智能问答。
5. 完整页尾：服务动作、官网入口、热线。

### 3.2 登录后服务概览

登录后不再使用营销首屏或大红色统计块，而采用浅色工作台：

```text
问候与“发起维修”
├─ 当前维修任务舱（深色）
│  ├─ 当前设备与板卡
│  ├─ 维修进度轨道
│  ├─ 当前节点、下一步、预计动作
│  └─ 查看详情
├─ 服务概览（浅色小统计）
│  ├─ 处理中 / 待补资料 / 已完成
├─ 我的设备
│  └─ 机型、保修、最近服务、快捷操作
└─ 服务动态
   └─ 工单状态与用户待办
```

红色仅用于主动作、当前节点和异常；统计数据保持浅色、低对比、易扫描。

### 3.3 维修申请

- 顶部保留页面标题、当前步骤和“重新开始”。
- 左侧（移动端上方）是固定五步轨道：设备、物料、故障、摘要、核验提交。
- 右侧（移动端下方）是当前步骤工作区。
- 已完成步骤收起为摘要，始终保留已选机型、板卡和保修状态，避免长表单丢失上下文。
- 成功提交后进入工单详情或进度页，不依赖大面积成功弹窗。

### 3.4 进度、扫码和保修

- 进度页：一张当前案件任务舱 + 可展开的垂直时间线，默认突出下一步而非全部历史。
- 扫码页：板卡、物料、设备、保修按顺序确认；失败状态给出人工核验入口。
- 保修页：设备身份、保修结论、依据、下一步动作，不使用普通表单卡堆叠。

## 4. GSAP 交互方案

GSAP 是业务状态的编排层，不是装饰层。

| 场景 | 动效 | 触发与时长 | 限制 |
|---|---|---|---|
| 路由进入 | 页面主区按阅读顺序轻微进入 | 300-500ms，一次 | 不移动固定导航和页尾 |
| 当前任务舱 | 进度线推进至当前节点，当前节点一次呼吸 | 450-700ms；处理中可低频提示 | 不闪烁、不持续缩放整块卡片 |
| 数字统计 | `0` 递增至当前值 | 400-600ms，一次 | 不做循环跳动 |
| 设备选择 | 设备卡转场至申请页设备摘要 | GSAP Flip，300-450ms | 仅桌面/性能允许时启用 |
| 申请步骤 | 当前步骤进入、旧步骤摘要收起、轨道推进 | 250-450ms | 表单输入不被动画打断 |
| 扫码确认 | 板卡、设备、保修结果顺序点亮 | 每项 100-140ms 间隔 | 失败时直接显示错误与下一步 |
| 时间线 | 点击节点展开处理详情 | 200-300ms | 手机上使用点击，不依赖 hover |

### 实现约束

- 使用 `gsap.context()` 绑定 Vue 生命周期，路由离开和组件卸载时 `revert()`。
- 使用 `prefers-reduced-motion`：启用后取消位移、数字递增、节点呼吸，直接呈现最终状态。
- 所有网络等待使用局部 loading；动画不得伪装真实处理进度。
- 单次过渡不超过 700ms；超过 1 秒的仅限明确标记的“处理中”反馈。

## 5. 组件划分

| 组件 | 责任 | 数据来源 |
|---|---|---|
| `RepairPortalShell` | 导航、页尾、路由转场、减少动态策略 | 路由、运行时官网地址 |
| `CurrentServiceTask` | 当前工单、状态轨道、下一步 | 客户工单 API |
| `ServiceOverview` | 低强调统计和待办 | 客户工单 API |
| `DeviceIdentitySummary` | 机型、板卡、保修、绑定关系 | V8 机型字典、扫码/保修 API |
| `RepairStepRail` | 五步申请流程和摘要 | Repair 草稿状态 |
| `ServiceTimeline` | 工单历史与可展开详情 | 工单状态和物流数据 |
| `RepairMotion` | GSAP context、Flip、减少动态降级 | 纯前端状态，不写业务数据 |

## 6. 实施切片

### P0：视觉系统与概览

- 重做登录后概览为浅色工作台 + 深色当前任务舱。
- 移除巨型 Logo 水印、全红统计面板和非业务背景动效。
- 统一公共导航、页尾、间距、按钮和状态颜色。

验收：在 1440x900 和 390x844 下，主操作在首屏可见，文字不被背景或水印覆盖。

### P1：申请与进度

- 五步申请改为固定步骤轨道 + 当前工作区。
- 工单页改为当前节点优先的时间线。
- 补充资料、核验失败、空工单均有明确下一步。

验收：用户可从已选设备进入申请，切换步骤不丢失选择；在进度页 2 秒内可识别当前状态和下一步。

### P2：GSAP 业务动效

- 实施路由进入、任务进度、步骤切换、时间线展开与设备卡 Flip。
- 加入减少动态和低性能降级策略。

验收：普通模式动画流畅且不阻塞操作；减少动态模式没有持续或位移动画；切换路由后无残留动画节点。

## 7. 测试与验收

| 类别 | 验收项 |
|---|---|
| 路由 | `/support`、`/repair/new`、`/requests`、`/warranty`、`/scan/:token` 可直接访问且不 404 |
| 数据 | 机型来自 `rjfinshed.model_dictionary`，接口 `source=V8:model_dictionary` |
| 业务 | 登录、发起申请、保修核验、扫码、查询进度保持原有 API 契约 |
| 视觉 | 桌面和手机无文本重叠、水平溢出、巨型水印遮挡或多个同权主按钮 |
| 动效 | GSAP 仅作用于页面/任务状态；减少动态偏好可用；路由离开正确清理 |
| 性能 | 不因动效增加首屏阻塞；按需加载 GSAP/Flip；监控客户端 bundle 增量 |

## 8. 风险与决策

- 风险：把 Repair 做成官网展示页会损害高频业务效率。
  决策：登录后以服务任务为中心，不复用营销首屏。
- 风险：GSAP 被用于装饰，造成性能和可访问性问题。
  决策：每个动效必须对应设备确认、步骤推进、工单状态或用户操作。
- 风险：独立应用复制 Nuxt 组件导致维护分叉。
  决策：只维护同一视觉契约和设计 token，不跨应用直接引用组件。
